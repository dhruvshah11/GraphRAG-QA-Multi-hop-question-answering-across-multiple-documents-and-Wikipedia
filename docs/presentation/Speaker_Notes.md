## Slide 1 — Title

*~234 words*

Good morning. We are Dhruv Shah and Manasvi Saxena, and this project was done under Dr. Sujoy Chatterjee at the School of Computer Science, UPES Dehradun. Our project is GraphRAG-QA: multi-hop question answering across multiple documents using evidence graphs and graph neural networks. It is our B.Tech final-year project in Natural Language Processing.

In one sentence: the system answers questions whose answer is spread over two or more documents. It retrieves passages with a hybrid dense-plus-keyword retriever, connects them in an evidence graph through shared entities, searches that graph for multi-hop evidence chains, reranks the evidence with either a graph heuristic or a trained graph attention network, and then produces an answer that is accepted only if it is grounded in cited sentences. If the evidence is not good enough it says so instead of guessing.

The graphic on the right is the idea in miniature: a question node, passages and entities, and one highlighted path through a shared entity that links two documents.

Everything runs locally on a laptop CPU: no GPU, no paid API. All numbers in this talk are measured and come from the results folder of the repository; we will be explicit about where the approach helps and where it does not.

The talk has four parts: problem and motivation, system design, the methods in detail, and the evaluation with an honest discussion of results and limitations, followed by questions.

## Slide 2 — Project introduction

*~225 words*

GraphRAG-QA is a complete question-answering application, not just a model. A user uploads PDF, TXT or DOCX files and asks a natural-language question. The system answers with the final answer, the supporting sentence, the reasoning separated into facts and inference, the evidence chain with the bridge entity, and citations down to document, page, chunk and exact sentence.

The key capabilities are on the left. Retrieval is hybrid: FAISS over MiniLM sentence embeddings plus BM25. On top of retrieval we build an evidence graph of documents, passages and named entities, and search it for multi-hop chains. The chains are reranked either by a Personalized-PageRank heuristic or by a graph attention network that we actually trained on HotpotQA. The answer generator is a local Flan-T5 model with an extractive reader as fallback, and a grounding check that rejects anything not found in the evidence.

The example on the right is our running example for the whole talk. The question never names the person. The Nobel PDF tells us the laureate from Toronto is Geoffrey Hinton; a separate text profile tells us Hinton's PhD is from the University of Edinburgh. The system links the two through the entity Geoffrey Hinton and cites both files.

Around the pipeline there is a seven-page React web application, an evaluation lab, a benchmark script and a pytest suite with 57 passing tests.

## Slide 3 — Problem statement

*~209 words*

Standard retrieval-augmented generation retrieves the passages that are most similar to the question. Multi-hop questions break this assumption, and this slide shows why with our running example.

The question describes a person without naming him: the 2024 Nobel laureate in Physics from the University of Toronto. The first passage, from the Nobel PDF, is very similar to the question because it shares Nobel, 2024, Physics and Toronto, so any retriever finds it. But it does not contain the answer.

The passage that does contain the answer is in a different file, the Hinton profile: he completed a PhD at the University of Edinburgh. This sentence shares almost no words with the question. It never mentions the Nobel Prize or Toronto in that sentence. So for a similarity-based retriever it looks irrelevant and is easily ranked below distractors. The only thing linking the two passages is the bridge entity, Geoffrey Hinton.

So our problem statement is: answer such questions over a user's own document collection or over Wikipedia; combine evidence from several sources; cite every source used; and refuse to answer when the evidence is insufficient, rather than hallucinating. Note that the last two requirements are as important as accuracy: an answer the user cannot verify is of limited value.

## Slide 4 — Motivation

*~203 words*

Four observations motivated the project.

First, real questions about reports, papers and policies often need facts from two or more documents. A student asking about a laureate's education, or an analyst combining a policy with a budget annex, is asking a multi-hop question.

Second, flat top-k retrieval misses the bridge passage, exactly as the previous slide showed. If we represent the collection as a graph in which passages are connected through the entities they share, the connection between the Nobel PDF and the Hinton profile becomes an explicit edge. That is also explainable: we can show the user the path the system followed.

Third, users must be able to verify answers. That means citations with page numbers and the exact supporting sentence, and it means the system must be able to say "I don't know" when the evidence is weak. In practice this safeguard matters more than a few points of accuracy.

Fourth, hand-designed graph scores only go so far. A graph neural network can, in principle, learn which neighbourhood patterns indicate evidence. We wanted to test that claim experimentally on real multi-hop data rather than assume it, so a trained GNN reranker is part of the system and part of the evaluation.

## Slide 5 — Objectives

*~204 words*

We set seven concrete objectives, each of which maps to a module of the code base and to a part of the evaluation.

One: ingest PDF, TXT and DOCX files while keeping page-level provenance, so that every citation can point to a page. Two: implement semantic retrieval with FAISS, lexical retrieval with BM25, and a configurable hybrid of the two. Three: build a heterogeneous evidence graph of documents, passages, entities and the question, and search it for multi-hop evidence chains.

Four, which is the research core: implement and actually train a graph attention network reranker, and compare it fairly against the retrieval baselines and against a graph heuristic, using measured metrics on held-out data. We deliberately say "actually train" because many student projects include an untrained GNN; ours refuses to use the GNN unless a compatible trained checkpoint exists.

Five: generate grounded answers that separate facts from inference, with validated citations and a confidence value computed from measurable signals. Six: support open-domain questions over Wikipedia using two-hop article retrieval. Seven: deliver a usable web application with an evaluation lab, a reproducible benchmark, tests and documentation, including the OOAD diagrams.

All seven objectives were implemented; the remaining slides show how, and what the measurements say.

## Slide 6 — Existing system

*~206 words*

This is how a conventional retrieval-augmented generation system works. The question is embedded, the top-k most similar passages are retrieved from a vector index, and a language model generates an answer from those passages. Lewis and colleagues introduced this pattern in 2020 and it is now the default way to build document QA.

Underneath, there are two families of retrievers. Lexical retrievers such as BM25 match exact terms and are strong on names, numbers and rare words. Dense retrievers such as Sentence-BERT or DPR embed question and passage into a vector space and match meaning, so they handle paraphrase.

For multi-hop questions, the research literature has graph-based models. HotpotQA introduced the benchmark; models such as DFGN and the Hierarchical Graph Network reason over entity graphs with trained BERT-sized encoders; more recent GraphRAG and HippoRAG systems use large language models to build knowledge graphs. These are powerful but are typically heavy: they rely on large models, GPUs or paid APIs, which does not fit a local, explainable system running on a laptop.

So the baseline we compare against in our own evaluation is exactly the top row: FAISS, BM25 and hybrid retrieval feeding the same answer generator. That keeps the comparison fair: only the evidence selection changes.

## Slide 7 — Limitations of existing approaches

*~219 words*

These are the specific weaknesses that GraphRAG-QA is designed to address.

First, similarity is not the same as relevance. In a multi-hop question the second-hop passage rarely resembles the question, so a retriever that scores passages by similarity alone systematically under-ranks it. Second, passages are scored in isolation. A conventional retriever has no notion that two passages from different files talk about the same person, so it cannot follow a link from one to the other.

Third, outputs are hard to verify. A generator that receives a bag of passages may combine them incorrectly or invent facts, and typical RAG demos show at best a list of source files, not the exact sentence that supports each claim. Fourth, there is usually no abstention: the system always produces an answer, even when the needed fact is not in the collection at all, which is the most dangerous failure mode for users.

Fifth, rankings are opaque and the strongest graph-based systems are heavy: they need large language models, GPUs or paid APIs, and the reason a passage was chosen is not exposed.

Each row on this slide corresponds to one component of our design: graph chains for the first two, grounding and citation validation for the third, the insufficient-evidence safeguard for the fourth, and a local, inspectable pipeline for the fifth.

## Slide 8 — Proposed system

*~209 words*

Our proposed system combines four ideas, shown as four pillars.

Pillar one, hybrid retrieval: FAISS over MiniLM embeddings captures meaning, BM25 captures exact terms, and we fuse them linearly with alpha equal to 0.7. This gives a stronger first hop than either retriever alone.

Pillar two, the evidence graph: a heterogeneous graph with four node types and six edge types. The important element is the bridge entity: an entity mentioned in a small number of passages links those passages, even across documents. Very frequent "hub" entities such as years are excluded because they would connect everything.

Pillar three, multi-hop reasoning: starting from the question we search simple paths of up to three hops through bridge entities, score each chain, and rerank passages either with a Personalized-PageRank heuristic or with a two-layer graph attention network trained on HotpotQA. Every strategy is computed on the same candidates so they can be compared fairly.

Pillar four, trustworthy answers: the generator's output is accepted only if it is found in the evidence; citations are validated sentence by sentence; confidence is computed from measured signals; and if any check fails the system returns "insufficient evidence".

Finally, the whole system runs locally on a CPU: no GPU, no paid API and no Docker are needed.

## Slide 9 — Technology stack

*~212 words*

This is the technology stack, layer by layer. Everything is open source and runs on a Windows laptop.

The frontend is a React single-page application built with Vite and TypeScript, styled with Tailwind CSS. The graph explorer uses React Flow, and the analytics charts use Recharts.

The backend is Python with FastAPI, served by Uvicorn, with Pydantic version 2 schemas for every request and response. Background jobs such as document processing and GNN training run in a single-worker job queue.

For NLP we use Sentence-Transformers with the all-MiniLM-L6-v2 model for 384-dimensional embeddings, spaCy's small English model for named-entity recognition and dependency parsing, and Hugging Face Transformers for the answer models: Flan-T5-base as a generator and TinyRoBERTa fine-tuned on SQuAD 2 as an extractive reader.

Retrieval uses faiss-cpu for exact cosine search and rank_bm25 for BM25. The graph is a NetworkX multi-directed graph, and the GNN is written in PyTorch with PyTorch Geometric's GATConv layer. Documents are parsed with PyMuPDF and python-docx. Persistent state lives in SQLite from the Python standard library plus files for the FAISS index, the graph and model checkpoints.

Testing uses pytest and FastAPI's TestClient. Diagrams were written in PlantUML and Mermaid; figures in matplotlib; and this presentation itself is generated by a python-pptx script from the result files.

## Slide 10 — Overall architecture

*~226 words*

This is the overall architecture, drawn as four layers.

At the top is the presentation layer: a React single-page application with seven pages: dashboard, document workspace, question answering, graph explorer, retrieval and GNN analytics, evaluation lab and settings. It talks to the backend only through a JSON REST API.

The API layer is FastAPI with Pydantic schemas, CORS and a background job queue. A composition root creates every service exactly once, so models are loaded once per process and are shared by the API, the scripts and the tests.

The processing core has two pipelines. The indexing pipeline runs when a document is uploaded: ingestion, chunking, named entities and relations, embeddings, the FAISS and BM25 indexes, and finally the corpus evidence graph. After every change an immutable corpus snapshot is rebuilt, so a query never sees half-updated indexes. The answering pipeline runs for every question: hybrid retrieval, the question subgraph, evidence chains, reranking with the heuristic or the GAT, grounded generation, and citation validation with confidence.

The storage layer is SQLite for documents, queries, answers and evaluation runs, plus the FAISS index file, the graph as JSON and GraphML, and the model files including the trained GNN checkpoint. In open-domain mode the answering pipeline calls the Wikipedia API instead of the local corpus, with a SQLite cache.

## Slide 11 — End-to-end workflow

*~220 words*

This slide follows one document and one question through the system, in six steps.

Steps one and two happen once per document. Upload validates the file type and size, stores it under a content-hash identifier so duplicates are detected, extracts the text page by page and normalises it. Indexing then chunks the text into sentence-aware chunks of 400 tokens with 80 tokens of overlap, runs spaCy named-entity recognition and relation extraction, embeds every chunk with MiniLM, adds it to FAISS and BM25, registers entities and rebuilds the corpus evidence graph, which is persisted to disk.

Steps three to six happen for every question. Ask embeds the question, computes FAISS, BM25 and hybrid scores and finds the entities mentioned in the question. Reason builds the question subgraph: the seed passages plus up to three hops of expansion through bridge entities. It then enumerates evidence chains and computes the graph heuristic and, if a trained checkpoint exists, the GNN scores.

Answer selects the evidence for the chosen strategy, the top chain first, generates a grounded answer, validates the citations and decides between answering and abstaining. Finally, Explore: the response includes the answer, fact and inference steps, the chain, the citations, every score and per-stage timings. The query, citations and subgraph are stored, which is what the graph explorer and analytics pages display.

## Slide 12 — Document ingestion & preprocessing

*~242 words*

Ingestion turns heterogeneous files into clean text with provenance. Each format has its own extractor. PDFs are read with PyMuPDF, one record per physical page, so citations can name the page. TXT files are decoded by trying UTF-8, UTF-16 and Windows-1252, and a form-feed character counts as a page break. DOCX files are read with python-docx in document order, including tables; heading styles start new sections, and explicit page breaks give logical page numbers.

Every upload is validated (extension, at most 25 MB, safe file name), and its identifier is derived from the SHA-256 hash of the bytes, so duplicates are detected. Normalisation applies Unicode NFKC, repairs words hyphenated across lines and collapses whitespace.

Chunking is sentence-aware: sentences are packed until the 400-token budget is reached, and the next chunk starts with up to 80 tokens of trailing sentences from the previous one. Chunks never cross a section boundary, and each chunk is an exact character slice of the document text, which is what lets us map any chunk back to its page.

On the chunks, spaCy extracts named entities and verb relations from dependency paths, and duplicate entities are merged conservatively, for example "Geoffrey E. Hinton" becomes "Geoffrey Hinton".

The measured numbers at the bottom are for the 5 bundled demo files: ingestion took 499 ms in total, producing 8 chunks of 142.4 tokens on average; entity extraction took about 15 ms per passage and found 156 mentions and 130 relations.

## Slide 13 — Semantic and lexical retrieval

*~222 words*

Retrieval produces the first hop and the candidate set for everything downstream, so we use two complementary retrievers.

Semantic retrieval embeds every passage with all-MiniLM-L6-v2 into a 384-dimensional, L2-normalised vector, so the inner product equals cosine similarity. Vectors live in a FAISS IndexIDMap2 over IndexFlatIP, which is exact search with stable identifiers, so documents can be added and removed incrementally and the index is persisted. Because the model reads at most 256 word pieces, long passages are embedded as the normalised mean of sentence windows of up to 180 words.

Lexical retrieval is BM25 Okapi with k1 = 1.5 and b = 0.75 over stemmed, stop-word-filtered terms. It is strong exactly where embeddings are weak: names, numbers, rare terms.

The hybrid score, shown in the box, is alpha times the clipped cosine plus one minus alpha times the BM25 score normalised by the best BM25 score for this question. Alpha is 0.7 by default and configurable. Candidates are the union of the top max(50, 5k) passages from each retriever.

All of this is fast: on the demo corpus, the mean query embedding takes 8.3 ms, FAISS search 4.0 ms, BM25 0.05 ms and the hybrid fusion 3.5 ms. On the held-out HotpotQA run hybrid retrieval had the best MRR and precision at 2 of the three pure retrievers, which justifies the fusion.

## Slide 14 — Knowledge graph construction

*~230 words*

The evidence graph is a heterogeneous NetworkX multi-directed graph. It has four node types: documents, passages, entities and, at query time, the question itself.

It has six edge types, and every edge is backed by extracted text or metadata, so the graph never invents connections. CONTAINS links a document to its passages. MENTIONS links a passage, or the question, to the entities it mentions, weighted by mention count. CO_OCCURS_WITH links two entities in the same sentence. RELATED_TO is a verb relation, such as "work at" or "acquire", and keeps its source sentence. SUPPORTS links a retrieved passage to the question, weighted by its hybrid score. CONNECTS_TO links two passages that share a bridge entity, or adjacent chunks of one document.

The bridge entity is the key concept. It is any non-date entity mentioned in between two and max_df passages, where max_df is max(4, min(40, a quarter of the passages)). Very frequent entities, such as a year or the name of a company mentioned everywhere, would connect everything and destroy the signal, so they are excluded.

On the demo corpus the graph has 118 nodes and 527 edges: 5 documents, 8 passages and 105 entities, and it is built in about 3.1 ms. The diagram on the left shows the fragment for our running example: both passages mention Geoffrey Hinton, which creates a CONNECTS_TO edge between passages in two different files.

## Slide 15 — Multi-hop evidence-chain retrieval

*~243 words*

Here is the multi-hop search on the running example.

The question node is connected to its hop-one passages: the hybrid top-k seeds plus passages that mention a question entity. Hop one here is the Nobel PDF passage, which says the prize went to John Hopfield and Geoffrey E. Hinton of the University of Toronto. Entity resolution has merged "Geoffrey E. Hinton" with "Geoffrey Hinton" by dropping the middle initial, so this passage and the Hinton profile share the bridge entity Geoffrey Hinton. That creates the CONNECTS_TO edge, and hop two is the profile passage stating that he completed his PhD at the University of Edinburgh. The chain therefore answers the question and cites both files.

Algorithmically, the question subgraph is expanded hop by hop, keeping the best twelve passages per hop, up to three hops. Chains are the simple paths from the question to candidate passages with NetworkX all_simple_paths, with a cutoff of max_hops; simple paths never revisit a node, which prevents cycles. We prune chains where a hop does not add any new question term.

Each chain is scored with the formula at the bottom: relevance anchored on the first passage, IDF-weighted coverage of the question terms, the quality of the bridge entities, and a small length penalty. The graph heuristic then combines the hybrid score with Personalized PageRank from the question node and the best chain score into one passage ranking. Every step carries a human-readable reason, which the UI shows.

## Slide 16 — GNN architecture — GAT reranker

*~243 words*

This is the graph attention network reranker, which we call GATReranker. It scores every passage node of the question subgraph with the probability that the passage is supporting evidence.

Node features are the element-wise product of the node embedding with the question embedding (384 values) plus 8 scalar relevance features such as cosine, BM25, hybrid score, hop distance and entity specificity: 392 inputs per node.

A linear layer projects these to 64 dimensions and adds a learned node-type embedding. Then come two GATConv layers from PyTorch Geometric, each with 4 heads of 16 dimensions. Attention is edge-type aware: the one-hot edge type enters the attention score, so a MENTIONS edge and a CONNECTS_TO edge can be weighted differently. Residual connections keep the node's own relevance signal while adding information from neighbours, for example a passage that shares a bridge entity with a highly relevant passage.

The scorer is an MLP over the concatenation of the initial representation h-zero and the final representation h-two. In addition there is a wide path: a linear term straight from the 8 scalar features to the logit, as in wide-and-deep models, because otherwise the strongest single signal gets diluted inside the projection. The sum goes through a sigmoid.

The model has 43,210 trainable parameters, trained with binary cross-entropy, 3 negatives per positive (half of them hard), Adam at learning rate 0.001 and early stopping on validation MRR. Without a compatible trained checkpoint the system never uses the GNN.

## Slide 17 — Answer generation and citations

*~249 words*

Answer generation is where most RAG systems lose the user's trust, so this stage is built around verification.

Step one selects the evidence: for the graph and GNN strategies, the passages of the top evidence chain come first, followed by the strategy's top passages, at most five. Step two generates. The default backend is Flan-T5-base on a compact context of the most relevant sentences, with a cautious prompt that may answer "unanswerable". If no generator is available, a TinyRoBERTa SQuAD-2 reader or a model-free extractive scorer is used.

Step three is the grounding check: the answer must occur in an evidence passage, or have token-F1 of at least 0.6 with an evidence sentence. Step four builds citations: for every claim, the supporting sentence is located in the cited passage; citations with support below 0.3 are removed.

The user sees the reasoning separated into facts, each quoting its sentence with a citation, and an explicit inference step, shown on the right for our example.

Confidence is a weighted sum of four measured signals: retrieval similarity, question-term coverage, chain score and answer support. It is not a calibrated probability, and we do not claim it is. If any hard check fails, such as best similarity below 0.22, coverage below 0.30, a named question entity missing from the evidence, the generator abstaining, no surviving citation, or confidence below 0.30, the system returns the insufficient-evidence message together with the failed checks. On the demo set, both unanswerable questions were refused by every strategy.

## Slide 20 — Experimental setup

*~258 words*

This slide defines the experiment so that the results on the next slides can be interpreted correctly.

The main evaluation set is a held-out sample of 300 HotpotQA questions from the official dev split, in the distractor setting: every question comes with ten Wikipedia paragraphs, of which exactly two are the gold supporting paragraphs. The GNN was trained on 3,000 questions from the official train split: the original 1,000-question sample plus 2,000 extra questions drawn so that they are disjoint from the training, validation and test sets. The 200 validation questions and the test set are unchanged, so there is no overlap with the test questions.

We also report the demo set: 12 hand-written questions over the five bundled files, including 7 multi-hop questions, 3 single-hop and 2 unanswerable ones. It was used during development, so its scores are optimistic and we do not draw conclusions from it.

Five strategies are compared: FAISS, BM25, hybrid, the graph heuristic and the GNN. Crucially, the analysis is computed once per question and every strategy selects evidence from identical candidates and uses the same generator, so only the evidence selection differs. For HotpotQA we use top-k 4, max hops 2 and K = 2.

Metrics are exact match and token F1 on the answer; precision at 2 and MRR on ranking; evidence recall, the share of gold passages that reached the generator; citations; and abstention. With two gold paragraphs, P@2 equals R@2.

Everything ran on a laptop CPU with 16 logical cores and 15.6 GB of RAM, Python 3.13.2, no GPU.

## Slide 21 — Performance evaluation

*~247 words*

These charts are drawn directly from the result files.

The chart on the left is the held-out HotpotQA test sample, 300 questions, for all five strategies on four metrics: exact match, F1, precision at 2 and evidence recall. Grey bars are the retrieval-only baselines; the two indigo bars are our graph-based strategies.

Reading it from left to right: on answer quality, the graph heuristic reaches EM 0.377 and F1 0.510, against 0.313 and 0.437 for hybrid retrieval; the GNN is on par at 0.373 and 0.498. On ranking, the GNN is now the best strategy: precision at 2 of 0.720, against 0.702 for the heuristic and 0.678 for hybrid. Evidence recall, the share of gold paragraphs that reach the generator, shows the biggest effect: 0.818 for hybrid, 0.898 for the graph heuristic and 0.910 for the GNN. That is the mechanism: chains bring the second-hop paragraph into the generator's context.

Top right is GNN training on 3,000 questions: validation MRR per epoch, against the hybrid and graph-heuristic baselines on the same validation graphs. The best epoch was 13 with MRR 0.947, above hybrid (0.926) and above the graph heuristic (0.937); early stopping ended training after 21 epochs, which took 179 seconds on CPU.

Bottom right is latency on the demo corpus: all graph reasoning, meaning question subgraph, chain traversal, PPR ranking and GNN inference, adds about 23 ms per question, while Flan-T5 answer generation takes about 0.76 s on CPU. Graph reasoning is therefore cheap; generation dominates.

## Slide 22 — Results and discussion

*~245 words*

This table repeats the main held-out numbers so we can discuss them precisely. The best value in each column is highlighted.

First, graph reasoning clearly helps. Compared with hybrid retrieval, the graph heuristic raises exact match from 0.313 to 0.377, which is +6.4 points, F1 by +7.3 points, and evidence recall from 0.818 to 0.898. The gain comes mainly from the 243 bridge questions, where EM goes from 0.337 to 0.407, because the chain pulls the second-hop paragraph into the context.

Second, trained on 3,000 questions, the GNN is the best passage ranker: P@2 0.720, which is +4.2 points over hybrid and +1.8 over the heuristic, and the highest evidence recall, 0.910. Its answer accuracy is on par with the heuristic, EM 0.373 versus 0.377, about one question in 300: the small Flan-T5 generator, not ranking, now limits the answers.

Third, data scaling is the key lesson. With only 1,000 training questions the same model reached P@2 0.677 and evidence recall 0.875 on the same test set, no better than hybrid; three times more data lifted it to 0.720 and 0.910. Feeding the heuristic score into the GNN as an extra feature was tried with the small data and rejected on validation (MRR 0.922).

Comparison questions remain hard for every strategy, EM between 0.211 and 0.263. The demo set is optimistic and only a functional check. The heuristic's test numbers moved by about one question against an earlier run because of multithreaded CPU floating-point nondeterminism.

## Slide 23 — Limitations and future scope

*~255 words*

We want to be explicit about the limitations.

The answer models are small and run on a CPU: Flan-T5-base and a SQuAD reader are far weaker than large language models, which is the main reason absolute exact match is modest and why comparison and yes-no questions are handled only partially. Entity recognition uses spaCy's small English model, which makes mistakes, for example labelling an organisation as a person, and every such mistake can add or remove graph edges. Entity linking is string-based, with no knowledge-base linking, and pronoun coreference is only approximated. Scanned PDFs are not supported because there is no OCR, and DOCX page numbers are logical rather than rendered pages.

The GNN was trained on 3,000 HotpotQA questions built from Wikipedia paragraphs. It is now the best ranker, but better ranking no longer turns into better answers, because the small generator is the bottleneck, and its behaviour on very different document styles is untested. Wikipedia mode needs network access and a contact User-Agent as required by Wikimedia policy; it is covered by tests with the HTTP layer stubbed, and we do not report measured live Wikipedia results.

For future work, the most promising directions are: a cross-encoder reranker; neural coreference and entity linking to Wikidata; question decomposition for comparison questions; continuing the data scaling that already paid off, and training the GNN jointly with the retriever; a stronger generator to turn better evidence into better answers; OCR; incremental graph updates instead of snapshot rebuilds; and, for deployment, streaming answers, authentication and multi-tenant collections.

## Slide 24 — Conclusion and Q&A

*~210 words*

To conclude.

We built a complete, local and explainable multi-hop question-answering system: ingestion of PDF, TXT and DOCX with page provenance, hybrid retrieval, a heterogeneous evidence graph, multi-hop evidence chains, a graph heuristic and a trained graph attention network for reranking, and grounded answer generation with validated citations, all behind a seven-page web application.

The central result is that graph reasoning measurably helps on held-out multi-hop questions: on 300 HotpotQA test questions, exact match rose from 0.313 with hybrid retrieval to 0.377 with the graph heuristic, and evidence recall from 0.818 to 0.898.

The trained GAT with 43,210 parameters, trained on 3,000 questions, is the best passage ranker: P@2 0.720 against 0.678 for hybrid and 0.702 for the heuristic, with the highest evidence recall of 0.910. Its answer accuracy is on par with the heuristic, because the small generator now limits answers. The lesson is data scaling: with 1,000 questions the same model did not beat hybrid ranking.

Finally, trust: every answer is cited down to the sentence, or the system says there is insufficient evidence, and the code base is backed by 57 passing automated tests and a reproducible benchmark.

## Likely viva questions (short answers)

**Q1. Why combine FAISS and BM25 instead of using only dense retrieval?**  
They fail differently: embeddings match paraphrase, BM25 matches exact names and numbers. On the held-out HotpotQA run hybrid had the best P@2 (0.678) and MRR (0.928) of the three pure retrievers (FAISS 0.615/0.895, BM25 0.637/0.896).

**Q2. How was α = 0.7 chosen?**  
It is the configurable default that weights semantic similarity higher while keeping a lexical component; the settings page and the benchmark accept other values. We did not run an exhaustive grid search, and we say so.

**Q3. What exactly is a bridge entity, and why exclude hubs?**  
A non-date entity mentioned in at least 2 and at most max(4, min(40, 25 % of passages)) passages. Entities that appear almost everywhere (years, the main company of a corpus) would connect every passage to every other and destroy the signal.

**Q4. How do you avoid cycles and combinatorial explosion in chain search?**  
Chains are simple paths (networkx.all_simple_paths, no node revisited) with a cutoff of max_hops (≤ 3); each passage keeps only its 6 best neighbours, at most 12 passages are kept per hop, and every hop must add a new question term.

**Q5. Why a GAT and not a GCN?**  
GCN averages neighbours with fixed weights; GAT learns attention weights per edge, and with edge features the weight can depend on the edge type (MENTIONS vs CONNECTS_TO). That matches the idea that some neighbours are evidence and others are noise. GAT is also inductive, which suits a new subgraph per question.

**Q6. How is the GNN trained — what are the labels?**  
Each HotpotQA training question is turned into a question subgraph exactly as at inference; the two gold paragraphs are positive passage nodes. Loss is binary cross-entropy with 3 negatives per positive (half hard negatives with the highest hybrid score), Adam lr 0.001, early stopping on validation MRR (patience 8).

**Q7. The GNN ranks best, so why is its EM not higher than the heuristic's?**  
Ranking improved (P@2 0.720 vs 0.702, evidence recall 0.910 vs 0.898), but EM 0.373 vs 0.377 is about one question in 300: the small Flan-T5 generator, not the evidence, is now the bottleneck. Comparison questions in particular are not solved by better ranking.

**Q8. What made the GNN work — architecture or data?**  
Data. With 1,000 training questions it only matched hybrid (test P@2 0.677, validation MRR 0.928); with 3,000 questions and the same architecture it reached test P@2 0.720 and validation MRR 0.947 (best epoch 13 of 21). A variant that fed the heuristic score into the GNN as a feature was rejected on validation (MRR 0.922).

**Q9. What is the 'wide path' in the GNN?**  
A linear term from the 8 scalar relevance features straight to the output logit (wide-and-deep). Without it the strongest single feature is diluted inside the 392-to-64 projection.

**Q10. How do you prevent hallucinated answers?**  
The generated answer must occur in the evidence (or have token-F1 ≥ 0.6 with an evidence sentence), every citation is validated against a located supporting sentence (support ≥ 0.3), and any failed hard check returns the insufficient-evidence message instead of an answer.

**Q11. Is the confidence score a calibrated probability?**  
No. It is a weighted combination of four measured signals (retrieval, coverage, chain, answer support) used for ranking and for the abstention threshold. Calibration would need a held-out reliability study.

**Q12. Why is absolute EM only around 0.3–0.4?**  
The readers are Flan-T5-base and a small SQuAD reader running on CPU; published HotpotQA systems use much larger readers trained on the full dataset. Our comparison is between evidence-selection strategies with the same reader.

**Q13. Why are P@2 and R@2 identical in the HotpotQA table?**  
Every HotpotQA question has exactly two gold paragraphs and K = 2, so precision@2 and recall@2 coincide.

**Q14. Can we trust the 1.00 EM on the demo set?**  
No. The 12 demo questions were written and used during development, so they are optimistic (the GNN scores 0.90 there because it misses the comparison question). Conclusions are drawn only from the 300 held-out HotpotQA questions.

**Q15. Was Wikipedia mode evaluated?**  
It is implemented and covered by tests in which only the HTTP layer is stubbed (search, parsing, caching, two-hop retrieval, graph, answering and citations run for real). Live use requires a contact User-Agent per Wikimedia policy; we report no measured live Wikipedia results.

**Q16. Where does the time go per question?**  
Graph reasoning (subgraph, chains, PPR, GNN) is about 23 ms; retrieval a few ms; answer generation dominates (Flan-T5 ≈ 0.76 s, reader ≈ 0.82 s, extractive ≈ 0.31 s on CPU).

**Q17. How would this scale to thousands of documents?**  
FAISS flat search is exact and linear; an IVF or HNSW index would be used at scale. BM25 and the graph are in memory; the snapshot rebuild after each change would be replaced by incremental graph updates (listed as future work). Query-time graph work stays small because it operates on the question subgraph only.

**Q18. What happens if there is no trained GNN checkpoint?**  
The GNN strategy falls back to the graph heuristic and the response says so; a checkpoint is used only if its feature-spec version and embedding model match the running system.
