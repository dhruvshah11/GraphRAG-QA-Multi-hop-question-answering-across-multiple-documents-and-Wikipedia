## Slide 1 — Title

Good morning. This is the technical version of our presentation on GraphRAG-QA: multi-hop question answering across multiple documents using evidence graphs and graph neural networks.

The short deck covers the story in about twenty minutes. In one sentence: the system retrieves passages with a hybrid FAISS plus BM25 retriever, links them in an evidence graph through shared entities, searches the graph for multi-hop evidence chains, reranks the evidence with either a graph heuristic or a trained graph attention network, and returns an answer only if it is grounded in cited sentences; otherwise it says that the evidence is insufficient.

## Slide 3 — Problem: single-hop RAG misses the bridge passage

Standard retrieval-augmented generation ranks passages by similarity to the question. A bridge question breaks that assumption. Our running example is demo question one: "From which university did the 2024 Nobel Prize in Physics laureate from the University of Toronto receive his PhD?"

The question describes a person without naming him. The Nobel PDF passage shares the words Nobel, 2024, Physics and Toronto with the question, so every retriever finds it, but it does not contain the answer. The answer sentence is in a different file, the Hinton profile: he completed his PhD at the University of Edinburgh. That sentence shares almost no words with the question. The only link between the two passages is the bridge entity Geoffrey Hinton.

This failure is measurable in our own benchmark file: with BM25 evidence the generator answered "Princeton University" for this question, an affiliation taken from the first-hop passage, while the graph and GNN strategies answered "University of Edinburgh". So the task is: answer such questions over the user's own documents or Wikipedia, combine evidence from several sources, cite every source, and refuse when the evidence is insufficient.

## Slide 4 — Motivation and objectives

Four observations motivated the project. Real questions about reports, papers and policies often need facts from two or more documents. Flat top-k retrieval misses the bridge passage, while a graph of shared entities makes that connection explicit and explainable. Users must be able to verify an answer, which needs sentence-level citations and an honest "I don't know". And a graph neural network can, in principle, learn which neighbourhood patterns indicate evidence; we wanted to test that claim on real multi-hop data instead of assuming it.

From this we derived seven objectives, which map one-to-one to modules of the code base: ingestion with page provenance; FAISS, BM25 and hybrid retrieval; the evidence graph and chain search; an actually trained GAT compared with baselines; grounded answers with validated citations and measured confidence; open-domain questions over Wikipedia; and a full web application with evaluation lab, benchmark, tests and documentation. Objective four is the research core. All seven were implemented; the rest of the deck shows how and what the measurements say.

## Slide 5 — Contributions and headline results

These are our five contributions, each with the measured number that supports it.

One, a complete, local and explainable system: ingestion, hybrid retrieval, evidence graph, chains, two rerankers and grounded generation behind a seven-page web application, all on CPU.

Two, graph-based evidence selection. On 300 held-out HotpotQA questions the graph heuristic raises exact match from 0.313 with hybrid retrieval to 0.377, and evidence recall from 0.818 to 0.898; the paired bootstrap test says this gain is significant.

Three, a GAT reranker with 43,210 parameters that we actually trained on 3,000 questions. It has the best ranking point estimates, P@2 0.720 and evidence recall 0.910, but against the heuristic the difference is not significant: the P@2 confidence interval is -0.003 to +0.042. We report it as a statistical tie.

Four, trust by design: grounding, entity grounding, validated citations and an explicit abstention message. Five, an honest evaluation with held-out data, confidence intervals, archived earlier runs and 57 passing tests.

## Slide 6 — Architecture: four layers and a composition root

The architecture has four layers. The presentation layer is a React single-page application with seven pages. It talks to the backend only through the JSON REST API.

The API layer is FastAPI with Pydantic v2 schemas, CORS for the Vite origin and a single-worker background job queue for document processing, evaluation runs and GNN training.

The key design element is the composition root in core/container.py. It creates every service exactly once: the embedding generator, the spaCy entity extractor, the graph builder, the GNN ranker, the graph reasoner, the answer generator, the corpus manager, the ingestion service, the open-domain retriever and the QA pipeline. Models therefore load once per process, and the API, the command-line scripts and the pytest suite all obtain their services from the same container, so they run exactly the same code.

The processing core has an indexing pipeline, triggered by uploads, and an answering pipeline, triggered by questions. After every document change the corpus manager rebuilds an immutable corpus snapshot, so a query never sees half-updated indexes. Storage is SQLite plus files for the FAISS index, the graph and the GNN checkpoint.

## Slide 7 — End-to-end pipeline with measured stage latency

This slide is the pipeline step by step, with the mean latency of every stage measured on the demo corpus: five files, 12 questions, 3 repeats, on the laptop CPU.

Indexing happens once per document. Ingestion of all five files took 499 milliseconds in total; chunking 1.2 ms; entity extraction about 15 ms and embedding about 27 ms per passage; building the FAISS and BM25 indexes and the corpus graph takes a few milliseconds.

Answering happens for every question: query embedding 8.3 ms, FAISS search 4.0 ms, BM25 0.05 ms, hybrid fusion 3.5 ms, the question subgraph 2.0 ms, chain traversal 3.8 ms, the PPR heuristic 4.8 ms and GNN inference 12.7 ms. Answer generation with Flan-T5 is about 757 ms. So all graph reasoning together costs about 23 ms per question; generation dominates.

## Slide 8 — Technology stack

Everything is open source and runs on a Windows laptop without a GPU.

The frontend is React with Vite and TypeScript, styled with Tailwind; the graph explorer uses React Flow and the charts use Recharts. The backend is Python 3.13 with FastAPI, Uvicorn and Pydantic v2.

The NLP models are all-MiniLM-L6-v2 from Sentence-Transformers for 384-dimensional embeddings, spaCy's small English model for named entities and dependency parses, Flan-T5-base as the generative answerer and TinyRoBERTa fine-tuned on SQuAD 2 as the extractive reader. Retrieval uses faiss-cpu and rank_bm25. The graph is a NetworkX MultiDiGraph and the GNN uses PyTorch with PyTorch Geometric's GATConv. PyMuPDF and python-docx parse documents; state is SQLite from the standard library plus index, graph and checkpoint files. Testing uses pytest with FastAPI's TestClient.

Optional backends, Ollama for a local LLM and the Claude API through the official SDK, are implemented behind the same interface but were never exercised in our runs; the system falls back to the local models automatically.

## Slide 9 — Document ingestion with page provenance

Ingestion turns heterogeneous files into clean text in which every character offset can be mapped to a page.

Each format has its own extractor. PDFs are read with PyMuPDF, page.get_text with sort enabled, one record per physical page. TXT files are decoded as UTF-16 when a byte-order mark is present, otherwise UTF-8, otherwise Windows-1252, and a form-feed character counts as a page break. DOCX files are read with python-docx in document order, including tables; paragraphs with Heading or Title styles start new sections, and explicit or last-rendered page breaks give logical page numbers.

Uploads are validated: the extension must be pdf, txt or docx, the file at most 25 megabytes and not empty, and the file name is sanitised against path traversal. The document identifier is "doc_" plus the first twelve hex characters of the SHA-256 of the bytes, so a repeated upload is detected as a duplicate. Normalisation applies Unicode NFKC, removes control and zero-width characters, repairs words hyphenated across line breaks and collapses whitespace.

The table on the right is measured: the five demo files, their page counts, characters and extraction times.

## Slide 10 — Sentence-aware chunking: 400 tokens, 80 overlap

Chunking decides what a passage is, and every later stage works on passages.

Tokens are word-level, defined by a regular expression for words and punctuation. The text is split into sentences by a rule-based splitter that protects abbreviations and initials. A sentence longer than the 400-token budget is split into token windows; that is the only case in which a sentence is cut. Otherwise consecutive sentences are packed greedily while the total stays within 400 tokens. The next chunk then steps back over trailing sentences of the previous chunk whose total is at most 80 tokens, which is the overlap, so a fact that straddles a boundary appears complete in at least one chunk. The code on the right is exactly that loop.

Chunks never cross a section boundary. Sections shorter than 25 tokens, such as a title, are merged into a neighbour: a leading one forward, any other one backward, with the titles joined. And every chunk is an exact slice of the document text, which our tests assert, so citations can highlight the exact characters.

On the demo corpus this produced 8 chunks with 142.4 tokens on average, in 1.2 ms. The documents are short, so most chunks are a whole section.

## Slide 11 — Named entities, normalisation and verb relations

Entities are the nodes that connect documents, so their quality directly shapes the graph.

We run spaCy en_core_web_sm over all chunks in batches of sixteen. Twelve labels are kept: people, organisations, geopolitical entities, locations, facilities, nationalities and groups, events, works of art, laws, products, languages and dates. Numeric labels such as cardinal, money and percent are dropped because they rarely identify the same real-world thing across passages. Dates are kept only if they contain a year or a month name, so "last week" is dropped. Mentions shorter than two or longer than eighty characters or eight words, and bare pronouns, are filtered.

Normalisation creates the identity key: NFKC, leading article and possessive removed, punctuation removed, dotted acronyms collapsed so U.S. becomes "us", ampersand becomes "and", and the result is case-folded.

Relations come from the dependency parse. For two entities in one sentence we find their lowest common ancestor; it must be a verb, at most three arcs from each entity. The label is the verb lemma, or the surface form for passives, plus the preposition introducing the second entity, for example "work at" or "born in". Bare be, have or do are dropped. On the demo corpus this produced 156 mentions and 130 relations, at about 15 ms per passage.

## Slide 12 — Conservative entity resolution and specificity

Entity resolution decides when two mentions are the same thing. A wrong merge creates false bridges between documents, so the registry is deliberately conservative: it merges only on four rules.

Rule one, identical normalised forms. Rule two, dropping middle initials, but only when the shorter form also occurs: this is how "Geoffrey E. Hinton" in the Nobel PDF and "Geoffrey Hinton" in the profile become one entity, which is exactly the bridge our running example needs. Rule three, a one-word PERSON mention equal to the surname of exactly one multi-word person, preferring the same document and only then the corpus. Rule four, an all-capitals acronym equal to the initials of exactly one multi-word entity, again same document first. Every surface form is kept as an alias, and every mention keeps its source chunk, so the resolution is traceable.

Specificity is an IDF-like weight in zero to one: one when an entity occurs in a single passage, lower as it spreads. It is used for bridge quality, subgraph expansion, PPR edge weights and as a GNN feature.

For questions, the registry's match function scores candidates: an exact alias 1.0, a dropped initial 0.95, a surname 0.85, a substring 0.6 plus 0.3 times the length ratio, and token Jaccard of at least one half scaled by 0.7. Only matches of at least 0.6 are used as question entities.

## Slide 13 — Dense retrieval: MiniLM embeddings in FAISS

Dense retrieval matches meaning. We embed every passage with all-MiniLM-L6-v2, which produces 384-dimensional vectors; they are L2-normalised so that the inner product equals cosine similarity.

The model reads at most 256 word pieces, but a chunk can have 400 tokens. Instead of silently truncating, passages longer than 180 words are split into sentence windows of up to 180 words, each window is embedded, and the passage vector is the normalised mean of the window vectors, as in the formula. Questions are embedded once and kept in an LRU cache of 512 entries; entity names have their own cache because the GNN embeds them for every subgraph.

The vectors live in faiss.IndexIDMap2 over IndexFlatIP. Flat means exact search, no approximation; IDMap2 gives stable 64-bit identifiers, so documents can be added and removed incrementally and vectors reconstructed. The index is persisted with a metadata file holding the model id and dimension; if the configured model changes, the index is rebuilt instead of mixing vector spaces. If the model cannot be loaded offline, a deterministic signed feature-hashing embedder is used and reported as degraded in the health endpoint.

Measured: embedding took about 27 ms per passage; per query, embedding 8.3 ms and FAISS search 4.0 ms.

## Slide 14 — Lexical BM25 and the hybrid score (α = 0.7)

Lexical retrieval is BM25 Okapi from rank_bm25, with k1 equal to 1.5 and b equal to 0.75, over content terms: lower-cased, stop-word-filtered and lightly stemmed, with question words like "which" removed from the query. Negative scores are clipped to zero. BM25 is strong exactly where embeddings are weak: names, numbers and rare terms.

The hybrid score combines both. The semantic part is the cosine clipped at zero, max of zero and cosine, so that dissimilar passages contribute nothing rather than a negative value. The lexical part is divided by the best BM25 score for this question, so it lies in zero to one and the best lexical match gets exactly one. Alpha is 0.7 by default and configurable on the settings page. The candidate set is the union of the FAISS top max(50, 5k) and the BM25 top max(50, 5k), ranked by hybrid score.

All per-passage scores are computed once per question in a QueryScores object and carried on every retrieved passage, which is what lets us compare all five strategies on identical candidates. On the held-out set, hybrid has the best P@2 and MRR of the three pure retrievers: P@2 0.678 against 0.615 for FAISS and 0.637 for BM25.

## Slide 15 — Heterogeneous evidence graph: node and edge types

The evidence graph is a NetworkX MultiDiGraph with four node types: documents, passages, entities and, at query time, the question. On the demo corpus it has 118 nodes and 527 edges: 5 documents, 8 passages and 105 entities, built in 3.1 milliseconds.

There are six edge types, and every edge is backed by extracted text or metadata; the graph never invents a connection. CONTAINS links a document to its passages. MENTIONS links a passage to an entity, weighted by the mention count, and at query time the question to its matched entities. CO_OCCURS_WITH links two entities in the same sentence, weighted by count. RELATED_TO is a verb relation and keeps its source sentence. SUPPORTS links each retrieved seed passage to the question, weighted by its hybrid score. CONNECTS_TO links two passages that share a bridge entity, weighted by the sum of the shared entities' specificities, or two adjacent chunks of the same document with weight 0.3. The last column shows the measured counts on the demo corpus; SUPPORTS and the question's MENTIONS edges exist only in a question subgraph. The graph is serialised to JSON, with a fingerprint used as a cache key, and to GraphML.

## Slide 16 — Bridge entities and question-subgraph expansion

Two rules decide which entities may connect passages. A bridge entity must not be a date, because two passages that mention 2024 are linked only by coincidence. And it must occur in at least two and at most max_df passages, where max_df is the maximum of 4 and the minimum of 40 and a quarter of the passages. Hub entities such as a year or the main company of a corpus would otherwise connect everything and destroy the signal.

For each question we then build a question subgraph. Hop one is the hybrid top-k seeds plus passages that mention a question entity, scored by hybrid plus 0.1 times the entity match score, keeping the best twelve. Each further hop takes passages that share a bridge entity with the previous hop, scored by hybrid plus 0.2 times the bridge's specificity, or adjacent chunks scored by hybrid alone, again keeping the best twelve, up to max_hops, which is 3 by default and 2 in the HotpotQA benchmark. We keep the question entities, entities shared by at least two included passages and the four most specific entities per passage, and copy only edges whose evidence lies inside the subgraph. On the demo corpus a question subgraph has on average 57.1 nodes and 209.1 edges and takes 2.0 ms to build.

## Slide 17 — Evidence-chain search with all_simple_paths

An evidence chain is a path from the question through passages, where consecutive passages share a bridge entity or are adjacent chunks of one document.

First we build a small undirected passage graph. It has the question node, an edge from the question to every hop-one passage, and the CONNECTS_TO edges between included passages. For each such edge we pick the shared entity that is best anchored to the question: its quality is 0.5 times its specificity plus 0.5 times its anchor, where the anchor is the match score of a question entity that the entity is, or co-occurs with, or is related to. To keep the search small, each passage keeps only its six best neighbours, ranked by the neighbour's hybrid score plus half the bridge quality.

Chains are then enumerated with networkx all_simple_paths from the question to every passage with cutoff max_hops. Simple paths never revisit a node, which prevents cycles, and at most 5,000 paths are examined. Three pruning rules apply: every passage needs a hybrid score of at least 0.05; every hop after the first must add at least one new question term, otherwise it cannot improve the evidence; and chains over the same set of passages are de-duplicated, keeping the best. The top eight chains are returned, each step carrying a human-readable reason. Measured traversal time on the demo corpus is 3.8 ms; the average top chain has 1.83 passages.

## Slide 18 — Chain score: anchored relevance, IDF coverage, bridges

This is the chain score exactly as implemented in traversal.py. Every term lies in zero to one.

The relevance term is anchored. The first passage counts 0.7 and the mean of the later passages 0.3. We do not simply average, because a bridge passage holds the second fact and is often only weakly similar to the question; averaging would punish exactly the hop that multi-hop questions need.

Coverage is IDF-weighted: each question content term gets a weight equal to its BM25 IDF divided by the largest IDF among the question terms, floored at 0.15, so a rare term like "Nobel" matters more than a generic term like "company". Coverage is the weighted share of question terms that appear anywhere in the chain's passages.

The bridge term is the mean quality of the bridge entities used by the chain, where quality is half specificity and half anchoring to the question, and it only applies to chains with more than one passage. Finally there is a small length penalty of 0.03 per extra hop, so a longer chain must earn its length through coverage.

The weights 0.45, 0.40, 0.15 and 0.03 are the defaults of the ChainWeights dataclass. They were set by hand on the development set, not learned; the GNN later re-scores the same chains with its own passage probabilities.

## Slide 20 — Graph heuristic: hybrid + PPR + chain support

The graph heuristic is the non-neural graph reranker. It needs no training and is always available.

It has three components. The first is the hybrid score. The second is Personalized PageRank on the undirected question subgraph, restarting at the question node with damping 0.85, normalised by the largest passage PPR. Edges are weighted by type: SUPPORTS 2, MENTIONS and RELATED_TO 1, CO_OCCURS_WITH and CONNECTS_TO 0.5, CONTAINS 0.2, and every edge that touches an entity is multiplied by that entity's specificity, floored at 0.05, so generic hub entities spread little relevance. The third component is chain support: the best score of any chain containing the passage, divided by the best chain score overall.

The final score is one half hybrid plus one quarter PPR plus one quarter chain support. The intuition: a passage is good evidence if it matches the question, if relevance flows to it through the graph, and if it sits on a good chain. On the held-out set this raises exact match from 0.313 to 0.377 and evidence recall from 0.818 to 0.898. The ranking takes 4.8 ms per question on the demo corpus.

## Slide 21 — Node features: spec gat-features-v1

The GNN sees exactly the question subgraph that the heuristic sees, converted into a PyTorch Geometric Data object by features.py. The feature specification is versioned; the trained checkpoint records "gat-features-v1".

Every node gets a vector of 392 numbers. The first 384 are the element-wise product of the node's text embedding with the question embedding, which is a question-aware semantic signal: dimensions where both agree light up. The node's text embedding depends on its type: the question uses its own embedding, a passage its index vector, an entity the embedding of its canonical name, and a document the normalised mean of its passages in the subgraph.

Then come 8 scalar features, listed in the table: cosine to the question, BM25, hybrid score, whether the passage was a retrieval seed, hop distance divided by six, whether an entity is a question entity, normalised log-degree and entity specificity. Passage-only and entity-only features are zero for other node types.

Edges are made bidirectional, and the edge type is one-hot encoded over the six types as edge_attr, so attention can depend on the type of connection. The node type is not part of x; the model adds a learned node-type embedding.

## Slide 22 — GATReranker architecture

This is the GATReranker in gnn/model.py. A linear layer projects the 392-dimensional input to 64 dimensions, adds the learned node-type embedding and applies ReLU: that is h-zero. Two GATConv layers from PyTorch Geometric follow, each with 4 heads of 16 dimensions concatenated back to 64, with the six-dimensional edge-type one-hot as edge features inside the attention. Each layer is followed by ReLU, a residual connection to its input, and dropout 0.2. The residuals keep the node's own relevance signal while adding neighbourhood information, for example that a passage shares a bridge entity with a highly relevant passage.

The scorer is an MLP over the concatenation of h-zero and h-two, from 128 to 64 to one logit. In addition there is a wide path, a linear term from the 8 scalar features straight to the logit, as in wide-and-deep models: without it the strongest single feature, the hybrid score, is diluted inside the 392-to-64 projection. The sigmoid of the logit is the probability that the passage is supporting evidence.

The table on the right counts the parameters per block from the configuration; they add up to 43,210, which matches the 43,210 trainable parameters reported by the training run. That is a deliberately small model: it has to train on CPU in minutes.

## Slide 23 — GAT equations: edge-type-aware attention

These are the equations of the model. h-zero is the ReLU of the input projection plus the node-type embedding.

In each GATConv layer, the attention coefficient from node j to node i is a softmax over i's neighbours of a LeakyReLU of a learned vector a applied to the concatenation of the transformed features of i, of j, and of the transformed edge feature, which here is the one-hot edge type. So the model can learn, for example, that information arriving over a CONNECTS_TO edge through a bridge entity matters more than over a CO_OCCURS_WITH edge. The new representation of i is the attention-weighted sum of its neighbours' transformed features, computed for 4 heads and concatenated.

Each layer adds ReLU, a residual connection and dropout. The passage score is the MLP of h-zero concatenated with h-two plus the wide linear term on the scalar features, and the probability is the sigmoid.

Why GAT and not GCN: GCN averages neighbours with fixed degree-based weights, while GAT learns a weight per edge, and with edge features the weight can depend on the edge type. GAT is also inductive, which suits a new subgraph per question. Attention weights can be returned for inspection; a unit test checks this.

## Slide 24 — Training: HotpotQA subgraphs, BCE with half-hard negatives

Training data comes from HotpotQA in the distractor setting. Every question has ten Wikipedia paragraphs, exactly two of which are the gold supporting paragraphs. Each question becomes its own small corpus, one passage per paragraph, and is turned into a question subgraph exactly as at inference time, with top-k 4 and max hops 2. The gold paragraphs are the positive passage nodes. Graphs are cached on disk per feature specification and embedding model, so they are built only once.

We trained on 3,000 graphs: the 1,000-question train sample plus 2,000 extra questions, all from the official train split and disjoint from validation and test, and validated on 200.

The loss is binary cross-entropy on passage nodes with negative sampling, resampled every epoch: per graph, up to 3 negatives per positive, half of them hard, meaning the non-gold passages with the highest hybrid score, and half random. Hard negatives force the model to beat the retrieval baseline rather than separate trivially irrelevant passages. Optimiser Adam, learning rate 0.001, weight decay 0.0001, batches of 16 graphs, at most 40 epochs, seed 42. Early stopping uses validation MRR with patience 8; ties are broken by lower validation loss, and the best checkpoint is saved.

## Slide 26 — Data scaling: 1,000 → 3,000 training questions

This is the most important lesson about the GNN: data, not architecture, made the difference.

Our first GAT was trained on the 1,000-question sample. Its best validation MRR was 0.928, barely above hybrid's 0.926, and on the same 300 test questions it reached P@2 0.677, evidence recall 0.875 and EM 0.367: it did not beat hybrid ranking, whose P@2 is 0.678. Its best epoch was 2, a sign that it over-fitted quickly.

We tried a feature variant, feeding the heuristic score in as a ninth feature; on validation it was worse, MRR 0.922, so it was rejected and never evaluated on test. Then we added 2,000 further disjoint training questions with the same architecture and settings. Validation MRR rose to 0.947, and test P@2 to 0.720, evidence recall to 0.910, EM 0.373.

All rows use the same validation and test sets, and the superseded runs are archived in results/previous_runs, so every number on this slide can be traced.

## Slide 27 — Model selection protocol and checkpoint compatibility

Two engineering safeguards make the GNN results trustworthy.

First, the selection protocol. Every model decision, the epoch, the feature variant and the training-set size, was made on the 200-question validation split, which comes from the official HotpotQA train split. The 300 test questions come from the official dev split and were evaluated once per adopted model; the rejected v2 variant never saw the test set. The extra training questions were drawn with a different seed and explicitly exclude every id in the train, validation and test files.

Second, checkpoint compatibility. The checkpoint stores its configuration, its state dict and metadata: training source, embedding model, feature-spec version and the training summary. GNNRanker loads it only if the feature-spec version equals the code's current version and the embedding model equals the running embedder. A randomly initialised model is never used. If there is no compatible checkpoint, the GNN strategy falls back to the graph heuristic and the response says so in its notes. The checkpoint is reloaded automatically when its modification time changes, for example after a training job from the UI. Two unit tests cover this: an untrained ranker is not used, and a trained checkpoint loads and runs inference.

## Slide 28 — Evidence selection and the generator cascade

Answer generation starts with evidence selection. For the graph and GNN strategies, the passages of the top evidence chain come first, in chain order and labelled with their step and bridge entity; then the strategy's own ranking fills the remaining slots, up to five passages, or more if the chain is longer. For the retrieval-only strategies there is no chain, only their ranking.

In auto mode the backends are tried in a fixed order. First Flan-T5-base, a generative model that can compose facts from several passages. If it is unavailable, fails, or produces an ungrounded answer, the TinyRoBERTa SQuAD-2 extractive reader is tried, over every passage and over the concatenated chain. The model-free extractive scorer comes last and is only a fallback for missing models: if a model read the evidence and abstained, the extractive scorer is not allowed to overrule that verdict. Ollama and the Claude API can be selected explicitly with a strict JSON schema; they are implemented but were never exercised in our runs.

In the held-out benchmark CSV, Flan-T5 produced between 284 and 289 of the 300 answers per strategy and the reader between 9 and 16. Measured on the demo corpus, generation takes about 757 ms with Flan-T5, 817 ms with the reader and 307 ms with the extractive scorer.

## Slide 29 — Flan-T5: chain-focused snippets and two-pass prompting

Flan-T5-base reads at most 512 tokens, so we never feed it whole passages. The snippet builder works like this. If the evidence contains a chain of at least two passages, only the chain passages are used, because extra passages mostly add distractors; otherwise the three best passages. From each passage we keep the four most relevant sentences for a chain, three otherwise, scored by embedding similarity to the question plus 0.3 times question-term overlap plus a bonus of 0.3 when the sentence mentions the bridge entity. Heading fragments are skipped, and a sentence that starts with a pronoun such as "he" or "the company" brings its preceding sentence along, a cheap form of coreference. The whole context is capped at 330 words, and each line is prefixed with its citation number and document name.

Decoding is greedy with at most 32 new tokens; the support value is the mean token probability. The first prompt is cautious and allows "unanswerable". If the model abstains, a second, plain reading-comprehension prompt runs. Its answer is accepted only after grounding, with half the support, and with a warning in the response. An answer that merely repeats the question is rejected. Yes-no questions use a dedicated prompt and are labelled as an inference.

## Slide 30 — Grounding and entity grounding: catching hallucinations

Whatever backend answers, the answer must be grounded. A span answer is accepted only if it occurs in an evidence passage, case-insensitively or after SQuAD normalisation, or if it has a token F1 of at least 0.6 with an evidence sentence. The answer's citation is then moved to the passage where it was found. Yes or no answers cite the first two evidence passages and are labelled as inference.

Grounding alone is not enough, and the two examples on this slide are real answers stored by the running application. First, "What is the boiling point of liquid nitrogen in Kelvin?" Flan-T5 generated minus 38.8; that string is not in the evidence, so it was rejected, the reader then found no answer, and the system abstained.

Second, the harder case: "Who won the 2030 FIFA World Cup final?" The cautious prompt abstained, the second pass produced "South Korea", and South Korea does occur in the DeepMind document, because the AlphaGo match was held in Seoul. So it passed grounding, and its similarity, coverage and confidence were all above their thresholds. The only check that caught it is entity grounding: the question names an event, "World Cup", and none of the named question entities occurs anywhere in the evidence. The evidence is about something else, however similar it looks, so the answer was replaced by the insufficient-evidence message.

## Slide 31 — Citations, confidence and the abstention decision

Citations are validated claim by claim. The claims are the answer and every fact step of the reasoning. For each claim and each cited passage, the builder locates the best supporting sentence: support is 1.0 if the claim occurs verbatim, otherwise the share of the claim's content terms found in the sentence. Citations with support below 0.3 are removed, so a passage is never cited for a claim it does not support; inference steps may only reference passages that remain cited. Each citation stores document, page, section, chunk, the exact sentence with character offsets and all scores.

Confidence is computed from four measured signals, never by a language model: the best evidence cosine rescaled from the interval 0.10 to 0.70 onto zero to one, question-term coverage, the best chain score, and the generator's support, which is halved after a model abstention and zero if the answer was not verified. The weights are 0.30, 0.25, 0.15 and 0.30. It is not a calibrated probability: in the demo benchmark a wrong answer had a confidence of 0.95.

The answer becomes exactly "Insufficient evidence found to answer this question reliably." if any hard check fails: best similarity below 0.22, coverage below 0.30, entity grounding, generator abstained or unverified, no surviving citation, or confidence below 0.30. The failed checks are returned to the user.

## Slide 32 — Open-domain mode: two-hop Wikipedia retrieval

In open-domain mode the corpus is built per question from Wikipedia, through the MediaWiki Action API, which needs no key.

Hop one searches Wikipedia with the full question and with every non-date question entity, three titles for the question and two per entity, and fetches up to six articles as plain-text extracts. Articles are split into sections, skipping reference-like sections such as See also, References and External links, and chunked like uploaded documents, at most twelve chunks per article. Then comes the bridge hop: hybrid retrieval over the first-hop passages, and named entities in the best six passages that the question does not mention become bridge candidates, for example the person a question describes indirectly. Their articles, up to three, are fetched as hop two, and only the new passages are embedded. From there the normal pipeline runs, and citations name the article section and URL.

Search results and articles are cached in SQLite, so demos keep working offline after a first run. Wikimedia requires a User-Agent with contact details; it is read from GRQA_WIKIPEDIA_USER_AGENT, and without it Wikipedia answers HTTP 403, which the API reports clearly as a 503. Honest status: this mode was verified only by tests with a stubbed HTTP layer; we report no measured live Wikipedia results. The bundled Wikipedia demo set has 5 questions.

## Slide 40 — Metric definitions

These are the metrics exactly as evaluation/metrics.py computes them; nothing is estimated.

Answer quality: exact match is one if the SQuAD-normalised prediction equals a normalised gold answer, that is lower case, without punctuation, articles and extra spaces. F1 is the token-level F1 between prediction and gold, maximised over gold aliases. Both are averaged over answerable questions only.

Ranking, at passage level with K equal to 2: precision at K is the share of the top K that is gold, recall at K the share of gold passages in the top K. Every HotpotQA question has exactly two gold paragraphs, so with K equal to two, P@2 and R@2 coincide. MRR is one over the rank of the first gold passage. Rankings for the graph and GNN strategies list subgraph passages by their score first, then the rest by hybrid score.

Evidence recall is the share of gold passages inside the evidence actually given to the generator; it measures what the answer model could see. Citation coverage is the share of gold passages that were cited, citation precision the share of cited passages that are gold. Abstention accuracy is the share of unanswerable questions answered with the insufficient-evidence message, and the false abstention rate the share of answerable questions where the system abstained. An abstention on an unanswerable question scores EM and F1 of one.

## Slide 41 — Datasets and evaluation protocol

The main evaluation set is a held-out sample of 300 HotpotQA questions from the official dev split, in the distractor setting: every question comes with ten Wikipedia paragraphs, exactly two of them gold. It contains 243 bridge and 57 comparison questions. The GNN was trained on 3,000 questions and validated on 200, all from the official train split, so there is no overlap with the test set. HotpotQA is licensed CC BY-SA 4.0 and the sample is fetched through the Hugging Face datasets server, about ten megabytes; the full training file is never downloaded.

The demo set has 12 hand-written questions over the five bundled files: bridge, comparison, single-hop and two unanswerable questions. It was used during development, so its scores are optimistic.

The protocol is the important part. For each question the analysis is computed once, and every strategy selects its evidence from identical candidates and uses the same generator in auto mode. Only the evidence selection differs. For HotpotQA we used top-k 4, max hops 2 and K 2, chunks 400 over 80, alpha 0.7; for the demo set top-k 8 and max hops 3. Everything ran on a CPU with 16 logical cores and 15.6 GB of RAM.

## Slide 42 — Held-out HotpotQA results (300 questions, 5 strategies)

This is the main result table, read directly from results/retrieval_metrics.json. The best value in each column is highlighted; for false abstention lower is better.

Graph reasoning clearly helps on answers. Compared with hybrid retrieval, the graph heuristic raises exact match from 0.313 to 0.377, +6.4 points, F1 from 0.437 to 0.510, evidence recall from 0.818 to 0.898, and nearly doubles citation coverage.

The GNN has the best ranking point estimates: P@2 0.720 against 0.702 for the heuristic and 0.678 for hybrid, the highest evidence recall, 0.910, and the best citation precision, 0.714. Its exact match, 0.373, is level with the heuristic's 0.377: one question in 300. The significance slide shows that the GNN-versus-heuristic differences are not statistically significant.

MRR is about 0.93 for every hybrid-based strategy: the first gold paragraph is almost always ranked first, and the gains come from the second, bridge paragraph. Absolute EM is modest because the answers come from Flan-T5-base and a small reader on CPU; the comparison is between evidence-selection strategies with the same reader.

## Slide 43 — All five strategies on answer, ranking and evidence metrics

The same held-out numbers as a chart, one colour per strategy, the same colours as every other chart in the project: blue FAISS, orange BM25, green hybrid, amber graph heuristic and pink GNN.

Read the groups from left to right. On exact match and F1, the two graph strategies, amber and pink, are clearly above the three retrieval-only strategies. ## Slide 44 — Statistical significance: paired bootstrap, 95 % CI

How sure are we? scripts/significance_test.py resamples the 300 test questions 10,000 times with seed 0, paired, so both strategies are always evaluated on the same resampled questions, and reports the mean difference with a 95 percent confidence interval. A difference is significant when the interval excludes zero. Filled dots are significant, hollow dots are not.

Graph-based reranking significantly beats retrieval alone. GNN minus hybrid: exact match +0.060, P@2 +0.042 and evidence recall +0.092, all with intervals above zero. The graph heuristic minus hybrid is also significant on all three.

But the GNN versus the heuristic is not significant on any metric. P@2 is +0.018 with an interval from -0.003 to +0.042; evidence recall +0.012, from -0.007 to +0.030; exact match -0.003. So the honest claim is: the trained GNN has the best point estimates for ranking, but it is statistically tied with the heuristic on this test set. Three hundred questions are not enough to separate them.

## Slide 45 — Per question type: bridge vs comparison

HotpotQA has two question types, and they behave very differently.

On the 243 bridge questions, the type our system is designed for, the graph strategies help most. Exact match goes from 0.337 with hybrid to 0.407 for both the heuristic and the GNN, and evidence recall from 0.790 to 0.887 and 0.903. This is exactly the second-hop paragraph being pulled in.

On the 57 comparison questions, such as "which was founded first", every strategy is weak: exact match between 0.211 and 0.263. Both entities are usually named in the question, so retrieval already finds both paragraphs, and evidence recall is high for everyone. The bottleneck is the small generator, which cannot reliably compare two dates or values. Here the GNN's exact match, 0.228, is even below the heuristic's 0.246. Question decomposition for comparisons is therefore on our future-work list.

## Slide 48 — Caveats we state explicitly

Before the conclusions, four caveats that qualify the numbers.

First, the demo set. The 12 demo questions were written and used while developing the pipeline, for example to tune the context construction for Flan-T5, so their scores are optimistic: the graph heuristic reaches EM 1.00 there. We use the demo set as a functional check, never for conclusions. It is still informative: every strategy refused both unanswerable questions.

Second, nondeterminism. Re-running the benchmark moved the graph-heuristic row by about one question: P@2 from 0.703 in the archived run to 0.702 now, evidence recall from 0.897 to 0.898. Multithreaded CPU inference is not bit-exact, so differences of that size are noise, which is also what the bootstrap intervals say.

Third, the Ollama and Claude answer backends are implemented behind the same interface but were never exercised: no local model was configured and no API key was set. Fourth, Wikipedia mode was verified only with a stubbed HTTP layer; live calls need GRQA_WIKIPEDIA_USER_AGENT set to your own contact details, and we report no live results.

## Slide 49 — Limitations and future work

The limitations, honestly. The answer models are small and run on CPU, so absolute exact match is modest and comparison and yes-no questions are handled only partially; better evidence no longer turns into better answers, which is why the GNN's ranking gains do not show up in exact match. spaCy's small model makes NER mistakes, for example labelling an organisation as a person, and every such mistake adds or removes graph edges. Entity linking is string-based, without a knowledge base, and coreference is only approximated. There is no OCR for scanned PDFs, and DOCX page numbers are logical rather than rendered. The GNN was trained on 3,000 Wikipedia-paragraph questions; its behaviour on very different document styles is untested, and on 300 test questions it is statistically tied with the heuristic. The chain weights are hand-set. The confidence is not calibrated.

For future work: a cross-encoder reranker; neural coreference and entity linking to Wikidata; question decomposition for comparison questions; more training data, since scaling already paid off once, and training the GNN jointly with the retriever; a larger test set to separate the GNN from the heuristic; a stronger generator; OCR; incremental graph updates instead of snapshot rebuilds; calibration of the confidence; and streaming answers, authentication and multi-tenant collections for deployment.

## Slide 51 — Conclusion

To conclude. We built a complete, local and explainable multi-hop question-answering system: ingestion with page provenance, hybrid retrieval, a heterogeneous evidence graph, multi-hop chains, a graph heuristic and a trained graph attention network, and grounded generation with validated citations, behind a seven-page web application.

The central result: graph-based reranking significantly beats retrieval alone on 300 held-out HotpotQA questions. The heuristic raises exact match from 0.313 to 0.377, a difference of +0.063 with a confidence interval from +0.017 to +0.107, and evidence recall from 0.818 to 0.898.

The trained GAT, 43,210 parameters on 3,000 questions, has the best ranking point estimates, P@2 0.720 and evidence recall 0.910, but it is statistically tied with the heuristic: the P@2 difference of +0.018 has an interval that includes zero. Data made the difference: with 1,000 questions the same model did not beat hybrid ranking.

And trust: every answer is cited to the sentence or the system says the evidence is insufficient, backed by 57 passing tests. Thank you; we are happy to take questions.

## Slide 53 — Examiner Q&A (1/6): Concept, Retrieval (backup)

Backup answers, questions 1 to 6 of the viva script's section 5, in the same order and wording. Every number is read from the result files.

Q1: What problem does this solve? A: Multi-hop questions whose answer needs facts from two or more documents. The second-hop passage looks nothing like the question; the evidence graph reaches it through the shared entity.

Q2: What is the contribution / novelty? A: A CPU-only system combining hybrid retrieval, an LLM-free typed evidence graph, chain search, a trained edge-type-aware GAT and grounded generation with abstention, evaluated with a significance test. No SOTA claim.

Q3: How is this different from Microsoft GraphRAG? A: GraphRAG uses an LLM to build a corpus graph and community summaries for global questions. We build the graph with spaCy, use a per-question subgraph, and target cited multi-hop factoid QA on a CPU.

Q4: Why a graph at all? Why not just retrieve more passages? A: More passages = more noise for a small generator. The graph gives an explicit path. Evidence recall 0.818 → 0.898–0.910, significant.

Q5: Why hybrid, and why α = 0.7? A: Dense catches paraphrase, BM25 exact names. Hybrid P@2 beats FAISS by +0.063 and BM25 by +0.042, both significant. α is the default; no full sweep (an honest gap).

Q6: Why MiniLM? A: all-MiniLM-L6-v2: 384-d, fast on CPU, strong on sentence similarity. Its 256-word-piece limit is handled by averaging sentence windows and re-normalising.

## Slide 54 — Examiner Q&A (2/6): Retrieval, Graph (backup)

Backup answers, questions 7 to 12 of the viva script's section 5, in the same order and wording. Every number is read from the result files.

Q7: Why FAISS IndexFlatIP? A: Normalised vectors → inner product = cosine. Flat is exact and takes milliseconds here; IDMap2 allows removing a document's vectors. IVF/HNSW for millions.

Q8: Why 400-token chunks with 80 overlap? A: A few related sentences per chunk; the overlap avoids cutting a fact. Sentence-aware, tiny sections merged; configurable, changes trigger reprocessing.

Q9: How are entities matched across documents? A: Normalisation, then conservative rules: middle initials, unambiguous surname, acronym. String-based, no Wikidata linking (a stated limitation).

Q10: Why exclude dates as bridges? A: “2024” appears in unrelated passages; linking through it creates spurious chains.

Q11: How do you prevent cycles and path explosion? A: Simple paths only, ≤ 3 hops, ≤ 6 neighbours per passage, ≤ 5,000 paths, minimum relevance, and each hop must add a new question term.

Q12: What is Personalized PageRank doing? A: A random walk restarting at the question with probability 0.15; edges weighted by type (SUPPORTS 2.0 … CONTAINS 0.2), scaled by entity specificity.

## Slide 55 — Examiner Q&A (3/6): GNN (backup)

Backup answers, questions 13 to 18 of the viva script's section 5, in the same order and wording. Every number is read from the result files.

Q13: Describe the model. A: (node ⊙ question embedding, 384-d) + 8 scalars → linear + type embedding → 2× GATConv (4 heads, edge-type edge_attr, residual) → MLP on [h⁰‖h²] + wide path. 43,210 parameters.

Q14: Why GAT rather than GCN? A: GCN averages neighbours with fixed weights; GAT learns how much each neighbour and, with edge features, each edge type matters.

Q15: Why the wide path? A: Without it the strongest single signal (retrieval relevance) is diluted inside the 392-d projection; a linear term passes the scalars straight to the logit (wide & deep).

Q16: How was it trained? A: One graph per HotpotQA question; gold paragraphs = 1. BCE with 3 negatives per positive, half hard. Adam, early stopping on val MRR; best epoch 13 of 21.

Q17: How do you know it's really trained, and not memorising? A: Checkpoint loaded only if spec version and embedding model match; never random. Results on 300 test questions unseen in training or selection; extra set excludes val/test ids.

Q18: The GNN beats the heuristic by only 1.8 points of P@2. Is that real? A: No, not on this sample: 95 % CI [-0.003, +0.042] includes 0. Both graph rerankers beat retrieval significantly; scaling 1,000 → 3,000 questions lifted test P@2 0.677 → 0.720.

## Slide 56 — Examiner Q&A (4/6): GNN, Generation (backup)

Backup answers, questions 19 to 24 of the viva script's section 5, in the same order and wording. Every number is read from the result files.

Q19: Then why is EM not higher with a better ranker? A: The answer step is the bottleneck: evidence recall 0.910 but EM 0.373 with Flan-T5-base and a small reader on CPU.

Q20: What did not work? A: The v2 feature set (heuristic score as input) — val MRR 0.922, rejected on validation. The 1,000-question model (val MRR 0.928) did not beat hybrid.

Q21: How do you stop hallucination? A: Evidence-only input, answer grounding, entity grounding, citations with support ≥ 0.3, thresholds (similarity ≥ 0.22, coverage, confidence ≥ 0.30); else the fixed abstention message with reasons.

Q22: Is the confidence a probability? A: No — 0.30·retrieval + 0.25·coverage + 0.15·chain + 0.30·support, not calibrated. demo-10: GNN answer “OpenAI” (wrong) with confidence 0.95.

## Slide 59 — Extra formulas (backup)

Backup formulas for detailed questions.

The reader converts SQuAD-2 logits into a span probability by comparing the best span score, start plus end logit, with the most confident no-answer score at the CLS token, through a sigmoid; below 0.3 the reader abstains. The extractive scorer ranks evidence sentences by 0.5 times cosine plus 0.3 times question-term overlap plus 0.2 times an answer-type match. Hop scores for subgraph expansion are hybrid plus 0.1 times the entity match score at hop one and hybrid plus 0.2 times specificity later. Personalized PageRank is the stationary vector of a random walk that restarts at the question with probability 0.15. The bootstrap reports, for each pair, the mean of the paired per-question differences over resamples and the 2.5 and 97.5 percentiles as the confidence interval. Generator support for Flan-T5 is the mean probability of the generated tokens under greedy decoding.

## Slide 64 — Sequence diagram: GNN reranking (backup)

The GNN reranking sequence: the graph reasoner asks the GNN ranker for scores; the ranker checks that a compatible checkpoint is loaded, the feature builder converts the question subgraph into a PyTorch Geometric Data object with the node features and one-hot edge types, the GATReranker computes one logit per node, and the sigmoid probabilities of the passage nodes are returned and used both for the GNN ranking and to re-score the evidence chains.
